# AI Content Generation & Translation Tool — Folder Structure

A monorepo with a Next.js frontend and a FastAPI backend, communicating through a single typed TypeScript client. The frontend is the chat UI with side-by-side artifact view; the backend owns all LLM calls, prompt construction, and persistence.

---

## Top-level layout

```
ai-content-tool/
├── frontend/                    # Next.js 14 (App Router) + TypeScript
├── backend/                     # FastAPI + Anthropic SDK + Pydantic
├── docker-compose.yml           # Local dev: spins up both services
├── .env.example                 # Documents env vars for both sides
├── .gitignore
└── README.md
```

The two sides are completely independent — different package managers, different runtimes, different Dockerfiles. They communicate over HTTP only. The contract between them is OpenAPI, generated by FastAPI and consumed by the frontend's codegen step.

### Why the API client is 3 files, not 5

Each file changes for a different reason:

- `client.ts` changes when **infrastructure** changes (base URL, auth, retries, timeouts).
- `endpoints.ts` changes when the **API surface** changes (new endpoint, renamed param).
- `types.gen.ts` changes when the **backend schema** changes — automatically, via codegen.

That's the only justification for splitting. Don't split further until one of these files exceeds ~200 lines.

### The codegen workflow

```bash
# In frontend/
npm run gen:api    # fetches backend OpenAPI, regenerates types.gen.ts
```

Run this whenever the backend's Pydantic schemas change. Frontend types stay in lock-step with the backend automatically — the contract cannot drift.

### The three-layer architecture

```
HTTP request
    ↓
api/v1/*.py        ← Validates input via Pydantic, calls service, returns
    ↓
services/*.py      ← Business logic: builds prompts, calls Anthropic, parses streams
    ↓
repositories/*.py  ← Persistence: reads/writes the database
```

**Routers do nothing but plumbing.** All Anthropic calls, prompt logic, and the artifact-vs-chat parsing live in `services/`. Repositories abstract storage — start with SQLite locally, swap to Postgres later without touching services.

### Why `schemas/` is the contract

Pydantic models in `schemas/` are the source of truth for the API. FastAPI generates `openapi.json` from them, and the frontend's `types.gen.ts` is generated from that. Define types **once**, in Python, and TypeScript follows automatically.

## How the two sides talk

```
┌─────────────────────────────┐         ┌─────────────────────────────┐
│  frontend/                  │         │  backend/                   │
│                             │         │                             │
│  Component                  │         │  api/v1/generate.py         │
│      ↓                      │         │      ↓                      │
│  hooks/useStream.ts         │         │  services/generation.py     │
│      ↓                      │  HTTP   │      ↓                      │
│  api/endpoints.ts  ─────────┼────────▶│  services/anthropic_client  │
│      ↓                      │         │      ↓                      │
│  api/client.ts              │         │  Anthropic API              │
│                             │         │                             │
│  api/types.gen.ts ◀─────────┼─────────│  schemas/*.py (OpenAPI)     │
└─────────────────────────────┘         └─────────────────────────────┘
```

The frontend never imports anything from the backend directly. Every interaction goes through `api/endpoints.ts`, which uses types generated from the backend's OpenAPI schema. **One place to change, one place to break, one place to fix.**

## Local development

```bash
# Terminal 1 — backend
cd backend
uv sync
uv run uvicorn app.main:app --reload --port 8000

cd frontend
npm install
```

## Design principles

1. **Frontend doesn't know about Anthropic.** All LLM logic lives in the backend. The frontend only knows about `api.generate(request)`.
2. **The OpenAPI schema is the contract.** Pydantic schemas → OpenAPI → TypeScript types. Define once, never drift.
3. **Three layers in the backend** — HTTP, business logic, persistence. Each layer only talks to the layer directly below it.
4. **Components are grouped by UI zone**, not by component type. `sidebar/`, `chat/`, `artifact/` reflect what's on screen.
5. **One typed client in the frontend.** Three files (`client`, `endpoints`, `types.gen`) — split because each changes for a different reason, not because of size.
6. **API versioning from day one.** `/api/v1/` costs nothing now and prevents breakage when v2 ships.

---

## When to split further

This structure is sized for an MVP. Split when these triggers fire:

- **`endpoints.ts` > 200 lines** → split into `endpoints/generate.ts`, `endpoints/sessions.ts`.
- **Streaming logic gets complex** (reconnection, multiplexing) → pull `streaming.ts` back out of `client.ts`.
- **More than ~10 routers** → group `api/v1/` by domain.
- **Multiple frontends** (mobile, admin) → introduce a `packages/api-client/` shared workspace.

Refactoring takes minutes. Don't pre-build for scale you don't have yet.
